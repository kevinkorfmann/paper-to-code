# Same genotypes, different sweep statistics

This original example calls **scikit-allel 1.3.13** to calculate Garud's
haplotype homozygosity statistics. Three different phase assignments have
exactly the same unphased diploid genotypes, yet H12 changes from **1** to
**0.15625**. This is an exact counterexample about missing phase information,
not a simulated selective sweep, a phasing benchmark, or a selection claim.

All inputs are deterministic, constructed biallelic arrays. No random
operation, random seed, empirical genetic data, or reference panel is used.

## Estimand and inputs

The target is **empirical haplotype-frequency concentration within a specified
window**, conditional on the supplied phase. With sample haplotype frequencies
`p1 >= p2 >= ...`, the tool returns:

```
H1    = sum(p_i^2)
H12   = (p1+p2)^2 + sum_{i>=3}(p_i^2)
H123  = (p1+p2+p3)^2 + sum_{i>=4}(p_i^2)
H2/H1 = (H1-p1^2)/H1
```

Absent frequency ranks contribute zero. H12 merges the two most frequent
haplotype classes. These statistics can be used in sweep inference, but they
are not themselves selection coefficients, sweep probabilities, ages, or
proof of a hard or soft sweep. H2/H1 requires interpretation jointly with H12
and a suitable calibrated population model, not as a standalone label.

Input shape is `(3 variants, 40 haploid chromosomes)`, with adjacent columns
representing the two chromosome copies of each of **20 diploid individuals**.
Every individual has genotype **0/1 at every variant**. Thus all 60 unordered
diploid calls, and all three ALT counts of 20, are identical in these panels:

| Panel | Complementary chromosome pairs assigned to individuals | Haplotype counts |
| --- | --- | --- |
| Two haplotypes | 20 individuals with 000/111 | 20, 20 |
| Four haplotypes | 10 with 000/111; 10 with 001/110 | 10, 10, 10, 10 |
| Eight haplotypes | 5 each with 000/111, 001/110, 010/101, 011/100 | 5 in each of 8 classes |

These are three compatible configurations, **not three equally probable
phases**. Population models, sequencing reads, pedigrees and reference panels
could favor some phases. The example does not establish that phase can never
be inferred; it shows that the unordered calls alone do not specify it.

## Actual output

Generated by the installed tool and stored in [sample_output.json](sample_output.json):

| Panel | H1 | H12 | H123 | H2/H1 |
| --- | ---: | ---: | ---: | ---: |
| Two haplotypes | 0.5 | 1 | 1 | 0.5 |
| Four haplotypes | 0.25 | 0.375 | 0.625 | 0.75 |
| Eight haplotypes | 0.125 | 0.15625 | 0.21875 | 0.875 |

Nothing about the unphased calls or sample size changed. H12=1 in the first
panel does not show that a sweep occurred. In particular, that panel has two
equally frequent haplotypes, not a single dominant haplotype.

For this specific genotype matrix, all possible phase configurations can be
summarized by four nonnegative complementary-pair counts `k1,...,k4` summing to
20. There are **1,771** such count vectors, ignoring which named individual
gets each pair. The counts give exactly:

```
H12 = [sum(k_i^2) + max(k_i)^2] / 800
```

A test enumerates every count vector, calls the real tool, and checks this
formula. The two- and eight-haplotype panels attain the sharp maximum **1**
and minimum **5/32**. These are discrete compatibility bounds, not confidence
limits or a posterior interval. Not every value between them is attainable.

### A practical reshape trap

In the pinned library, `GenotypeArray.to_haplotypes()` rearranges array axes.
It does **not** infer phase. Converting sorted unphased 0/1 calls this way
produces the two-haplotype panel, even when the input calls were obtained
from the eight-haplotype panel. This behavior is tested and recorded in the
output. Preserve actual phase information or use an appropriate phasing
method before applying a phased-haplotype statistic.

### Sample-frequency versus population homozygosity

H1 is the probability of matching labels in two draws **with replacement
from this empirical sample**. Our separate exact reference enumerates all
ordered chromosome pairs, including self-pairs, and merges labels explicitly
for H12 and H123. It does not use the library's haplotype-counting helpers.

Sampling two distinct chromosomes is a different calculation. For the
two-haplotype panel, that match probability is `19/39`, rather than H1=`1/2`.
The library does not apply a finite-sample correction to Garud's statistics.
Do not interpret the sample values as unbiased population estimates or apply
a generic H1 correction to H12 and H2/H1. No sampling uncertainty is estimated.

## Assumptions and limits

- Complete, correctly aligned, biallelic haplotypes and the specified phase are
  assumed. The wrapper rejects missing calls, noninteger or nonbinary alleles,
  empty windows and fewer than two haplotypes. Diploid conversion additionally
  requires an even number of chromosomes. Validation cannot establish phase.
  This educational wrapper caps the quadratic exact-pair oracle at 256
  chromosomes; that is not a limit imposed by scikit-allel itself.
- Every individual being heterozygous at all three sites is an intentionally
  extreme construction, **not a random-mating population sample**. No biological
  sampling, recombination, sequencing-error or sweep-generating process is fitted.
- Only three SNPs allow at most eight haplotypes, imposing a high baseline
  concentration. Window definition, marker ascertainment, sample composition,
  recombination, demography, relatedness and phasing errors matter in real scans.
  Do not import genome-scale significance cutoffs into this tiny example.
- The primary paper used substantially larger windows and demographic/selection
  comparisons. This example does not reproduce its scan or calibrate a null,
  p-value, confidence interval, false-positive rate or real-genome accuracy.
- A monomorphic control returns H1=H12=H123=1 and H2/H1=0. High concentration
  alone is not evidence of selection. Whole-chromosome relabeling leaves the
  statistics unchanged; changing relative phase across sites need not.

## Reproduce

Use **CPython 3.12.11** and the existing hash-locked scikit-allel environment:

```sh
python3.12 -m venv .venv-garud
. .venv-garud/bin/activate
python -c "import platform; assert platform.python_version() == '3.12.11'"
python -m pip install --require-hashes -r examples/inference_showcase/scikit_allel_fst/requirements.lock
python -m unittest discover -s examples/inference_showcase/garud_phase -v
python -m examples.inference_showcase.garud_phase.demo --check-sample
```

Recorded versions: CPython **3.12.11**, scikit-allel **1.3.13**, NumPy **2.3.5**.
The CLI emits JSON with floats rounded to nine decimals and verifies the
checked output byte for byte. Exact rational reference values are also saved.

The **32 tests** include the 1,771 full-sample phase-count configurations,
independent exact pair enumeration for all **490** unordered two-locus samples
of 2–8 chromosomes, and **340** labeled phase assignments for 1–4 diploids at
three loci (69 distinct count vectors, after ignoring individual order).
Additional checks cover unequal counts and sorting, invariant
transformations, self-pair versus distinct-pair probabilities, monomorphic
controls, the reshape trap, input validation, nonmutation, actual tool use,
CLI behavior and checked output. The existing scikit-allel CI job runs them
with the same locked dependencies. No new paid service or scheduled CI is added.
